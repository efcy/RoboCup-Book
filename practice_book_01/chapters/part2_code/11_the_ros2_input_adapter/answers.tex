  \item With $R=R_z(\psi)R_y(\theta)R_x(\phi)$ from trunk to world, the world's gravity direction $(0,0,-1)$ in the trunk frame is $R^\top(0,0,-1)^\top=(\sin\theta,\,-\sin\phi\cos\theta,\,-\cos\phi\cos\theta)$.
\begin{verbatim}
def gravity_from_rpy(rpy):
    roll, pitch = rpy[0], rpy[1]
    return np.array([np.sin(pitch),
                     -np.sin(roll) * np.cos(pitch),
                     -np.cos(roll) * np.cos(pitch)])
\end{verbatim}
Upright: $(0,0,-1)$. Pitch $30^\circ$: $(0.5,0,-0.866)$. Roll $90^\circ$: $(0,-1,0)$. Check the signs against the IMU convention of the robot by tilting it.

\begin{verbatim}
def make_joint_map(msg_names, model_names):
    pos = {n: i for i, n in enumerate(msg_names)}
    missing = [n for n in model_names if n not in pos]
    if missing:
        raise ValueError(f"not in message: {missing}")
    return np.array([pos[n] for n in model_names])
\end{verbatim}
  \item The callback runs in the adapter's thread at the topic's rate; anything slow there delays or drops sensor data, and logic there would run outside the blackboard order, so it would not be logged, replayed or tested like the rest. Calling the SDK from there would also bypass the safety layer.
  \item $3\cdot500=1500$\,ms per second: more than one core, which is impossible, so messages are dropped (keep last 1) or arrive late. Even at $1$\,ms it would be half a core. The callback must be short (a few array copies). If the GIL is busy, the callback waits too, and the measured age of the data grows.
  \item ``The message is old'': it was received some time ago; the adapter knows this from its own time stamp. ``The sensor value is old'': the value was measured some time before the message was sent (inside Booster's services). The adapter can only measure the first, unless the message carries a sensor time stamp from the same clock.
\end{enumerate}
